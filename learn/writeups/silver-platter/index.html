Silver Platter

TryHackMe · Linux · Easy. Web enumeration leads to a Silverpeas authentication bypass; private messages leak an SSH password; and a password reused in the system log takes us to root.

Targets and flag values are from a shared practice environment and are redacted here. The point is the method, not the answers.

1. Recon

Start with a full TCP port scan, then run service and script detection against whatever is open.

nmap -p- --min-rate 1000 -oA scans/all-ports TARGET
nmap -p 22,80,8080 -sC -sV -oA scans/services TARGET

What comes back

  • 22/tcp — SSH (OpenSSH). Password authentication is enabled, but we have no credentials yet.
  • 80/tcp — HTTP (nginx). A static “Hack Smarter Security” landing page.
  • 8080/tcp — HTTP. A separate application that returns a bare 404 on the root — worth fingerprinting properly.

2. Web Enumeration

Browse the port 80 site by hand first, then run a content scan for anything not linked.

gobuster dir -u http://TARGET -w /usr/share/wordlists/dirbuster/directory-list-2.3-small.txt

Reading the pages is what pays off here. The Contact section tells visitors to reach the project manager on “Silverpeas”, and names his username. That is two gifts at once: the software running on 8080 (Silverpeas, a collaboration platform) and a valid username to go after.

Takeaway

A directory brute force is useful, but the contact page — plain text anyone can read — is what identifies the application and the first account. Enumerate the content, not just the file system.

3. Silverpeas Auth Bypass

The default administrator login does not work, so we research the version instead. Silverpeas has a known authentication bypass (CVE-2024-36042): the login endpoint can be tricked into authenticating without a valid password when the password parameter is removed from the request entirely.

The technique

  • Submit the login form and capture the request in a proxy.
  • Delete the Password field from the request body (not blank — removed).
  • Forward it, and the application logs you in as the named user.

Logging in as the project manager account from the contact page lands us in the Silverpeas web interface.

4. Reading Private Messages (IDOR)

Inside Silverpeas, the private notifications are addressed by a numeric message ID in the URL. Nothing checks that the message belongs to you, so stepping the ID through nearby values reveals other users' messages — a textbook Insecure Direct Object Reference.

One of those messages is an administrator reminding another user (tim) of his password. We now have real SSH credentials.

ssh tim@TARGET
# authenticates with the password recovered from the message

The user flag is in tim's home directory.

cat ~/user.txt   # THM{...}

5. Privilege Escalation

First, see who we are and which groups we are in.

id
# uid=1001(tim) ... groups=...,4(adm)

Membership of the adm group is the whole game: it grants read access to the system logs. Searching the authentication log for anything password-related is a reliable habit.

grep -i pass /var/log/auth.log*

The log captured full docker run commands from an administrator, including a database password passed on the command line. That same password had been set for the tyler account — a reused secret. We switch to tyler, who can run sudo.

ssh tyler@TARGET
sudo su
cat /root/root.txt   # THM{...}

Why it worked

Two ordinary mistakes stacked up: secrets passed as command-line arguments end up in logs, and the same password was reused across a service and a user account. Either alone is a finding; together they are a straight line to root.

What To Take Away

  • Read every page. The contact page handed us the application and a username.
  • Match software to known CVEs before assuming a login is a dead end.
  • Try every credential on every service. Reuse is the most common real-world path to escalation.
  • If you can read logs, read them for secrets — especially command lines.
