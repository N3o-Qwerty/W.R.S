Edge

Hack Smarter · Windows · Assumed breach. Starting credentials, a stack of secrets left in desktop notes, and — the centrepiece — live credentials scraped straight out of Microsoft Edge's memory.

A Hack Smarter lab, shared with permission. Credentials, hostnames, and flag values are redacted — the point is the attack chain, not the answers.

1. Foothold over WinRM

The client provides a low-privilege account for an assumed-breach test. The host blocks ping (scan with -Pn) and exposes RPC, SMB and WinRM (5985). The starting credentials work over WinRM.

nmap -Pn -p- -sV TARGET            # 135, 445, 5985
evil-winrm -i TARGET -u jmorris -p 'STARTING_PASSWORD'

2. Secrets in Plain Sight

The user's documents are a case study in bad habits. IT tickets, an email draft and a password-policy file give up a surprising amount:

  • An email mentions a service-account password seen on a sticky note (“the password is terrible” — it is).
  • The password policy flags one service account with Kerberos pre-authentication disabled (AS-REP roastable) and another as weak.
  • Internal hostnames — an operations portal and a file server — and a lot of hints about password reuse.

Useful context, but none of it is the win on its own. The win is in a running process.

3. Dumping Edge's Memory

Microsoft Edge is running on the box, and a logged-in browser holds saved credentials in memory. A small tool takes a process snapshot of msedge.exe and carves username/password pairs out of the frozen memory — no disk access to the credential store needed. Cross-compile it, upload it over the WinRM session, and run it.

# build on Linux (MinGW)
x86_64-w64-mingw32-g++ edgeSnapper.cpp -o edgeSnapper.exe \
  -static -static-libgcc -static-libstdc++ -ldbghelp -lpsapi
# then: upload edgeSnapper.exe   (evil-winrm)  and run it
.\edgeSnapper.exe     # prints several user:password pairs from memory

The dump yields several credentials, including a VDI service account whose password is valid on the domain — a real privilege step, straight from browser memory.

4. Through the Ops Portal

The recovered VDI account logs into the internal operations portal (the one named in the notes), which exposes plant controls and settings. One control lets you launch a program by path — point it at cmd.exe and you have command execution from the web app.

C:\windows\system32\cmd.exe     # launched via the portal → shell

Poking around from there turns up a saved PuTTY session in the registry, and PuTTY stores session passwords in plain text. That hands over a management account.

reg query "HKCU\Software\SimonTatham\PuTTY\Sessions" /s
# ... UserName = svc_..._mgmt   Password = (stored in cleartext)

5. Administrator

The management account from the PuTTY session has the access we need. Log back in over WinRM as that account and read the flag from the administrator's desktop.

evil-winrm -i TARGET -u svc_..._mgmt -p 'STORED_PUTTY_PASSWORD'
type C:\Users\administrator\desktop\root.txt

What To Take Away

  • Credentials saved in a browser live in its process memory; anyone who can run code as that user can read them. Avoid storing corporate logins in the browser.
  • Desktop notes, tickets and email drafts leak secrets — treat user documents as part of the attack surface.
  • PuTTY saves session passwords in the registry in cleartext. Don't store them there.
  • Password reuse across accounts turned several small leaks into a full compromise.
